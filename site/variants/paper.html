THE REASON FOR THE SEPARATION

Data has a durable home.
Compute has a specific job.

Storage capacity, writer resources, and reader resources become separate planning decisions. The shared dataset stays in object storage while serving processes can be added or replaced.

1

One writer, a durable record.

The gateway sends PUT and DELETE to the writer. SlateDB persists through shared WAL and SST files in object storage before acknowledging durability.

2

Readers, provisioned separately.

Point GETs use SlateDB readers. Add reader compute independently from the writer; readers fetch shared data and cache working sets, without maintaining full separate durable copies.

3

A projection for the questions.

The writer exports table data and durable changes to Parquet in the background. Readers use DuckDB over published files, without a fresh SlateDB table scan for every query.

The gateway keeps no key-value cache. A durable acknowledgement, point-read visibility, and SQL publication are separate events. Poll reads when your application needs to observe a change.

THE INTERFACE / ASYNC RUST

Submit now.
Await durability.

RockBeeClient · JSON tables
use rockbee_client::{RockBeeClient, Result};
use serde_json::json;

async fn example() -> Result<()> {
    let client = RockBeeClient::connect("127.0.0.1:7100").await?;
    let products = client.table("products");
    let write = products.put(&json!({"name":"Keyboard"}));
    println!("submitted {}", write.id());
    let id = write.await?; // Durable ACK.
    products.put_key("book-42", &json!({"author":"Alice"}), None).await?;
    let document = products.get(&id).await?; // Eventual.
    let result = products.query(
        "SELECT id, value->>'name' AS name FROM products"
    ).await?; // Publication can lag.
    println!("WAL {}: {:?}", result.exported_wal_file_id, result.rows);
    products.delete(&id).await?;
    client.shutdown().await;
    Ok(())
}

put immediately starts a document write and generates a UUID, available before you await. Use put_key for caller-supplied IDs or replacements, and get or delete by ID.

Raw byte PUT, GET, and DELETE remain available on the same client. Keep your own encoding when a JSON table is not needed.

The SQL response includes selected rows as JSON objects and the published WAL watermark. Reader SQL memory, concurrency, and deadlines are configurable.

1
Durability, with an explicit boundary.
PUT and DELETE wait for SlateDB’s durable acknowledgement. Readers and Parquet publication may still lag. No immediate read-after-write guarantee.
2
Uncertainty, without automatic replay.
Mutation errors distinguish NotSent, Rejected, and Unknown. An uncertain mutation is never automatically replayed; an error is not a rollback acknowledgement.
3
Expiry, without an older value returning.
Optional TTL applies to bytes and documents. GET and SQL hide expired latest versions. Physical object removal can happen later.
4
Completion, even if the handle is dropped.
An admitted eager PUT keeps running when its handle is dropped. Shutdown drains admitted work. Optional CDC exports durable WAL changes as JSON lines.
