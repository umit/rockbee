01One write, clear boundaries

Know what success means.

Follow the lifecycle. Each boundary answers a different question about your data.

CLIENT / SUBMITTED

A handle, immediately.

Calling put eagerly starts the mutation. Keep the completion handle to observe success or a classified error. For a generated document, the UUID is already available.

Dropping a completion handle does not cancel a mutation that has already started.

RUST / WRITE LIFECYCLE
let write = products.put(&json!({
    "name": "Field keyboard", "price": 129
}));
let id = write.id().to_owned();

// The write has started. Keep its handle.
// Submission is not a durable acknowledgement.

WRITER / DURABLE ACK

The durable boundary.

The single writer persists through SlateDB before acknowledging success. This is what a successful await tells your application.

A durable acknowledgement is the mutation completion boundary, independent of reader lag.

RUST / WRITE LIFECYCLE
let write = products.put(&document);

write.await?;
// Success: the mutation was durably acknowledged.

// This does not assert immediate reader visibility.

READER / EVENTUAL GET

A reader catches up.

GET goes to a SlateDB reader through the gateway. It reflects that reader’s current view; a newly acknowledged mutation may still appear as an older value.

SlateDB owns the reader data cache. GET visibility and SQL publication are separate.

RUST / WRITE LIFECYCLE
let product = products.get(&id).await?;

// Reads the current reader view.
// Reader catch-up is independent of the ACK.
// Design your workflow for eventual convergence.

READER / PUBLISHED SQL

SQL gets its own view.

The writer exports JSON tables to immutable Parquet in the background. DuckDB on the reader queries that published projection, not the live writer.

A successful PUT does not mean the next SQL query already contains that mutation.

RUST / WRITE LIFECYCLE
let result = products.query(
    "SELECT id, value FROM products"
).await?;

// Real DuckDB SQL over published Parquet.
// SQL visibility follows background publication.
When a mutation does not complete successfully
NotSent
The client knows the request was not sent.
Rejected
The mutation was rejected rather than acknowledged as durable.
Unknown
The durable outcome is uncertain. An error does not establish that the mutation was absent.

Rockbee does not automatically replay uncertain mutations. Reconcile the outcome in your application before deciding what to do next.

02Your data, your shape

Use the shape
your application needs.

A

Opaque bytes, if that’s enough.

PUT, GET, and DELETE with your byte keys and values. Rockbee doesn’t interpret their contents.

B

JSON without a table schema.

Store JSON objects with fields that can vary by document. Use generated UUIDs or caller-supplied IDs, with optional TTL.

C

SQL when a key isn’t the question.

Use real DuckDB SELECTs over the published Parquet projection. The table exposes id as VARCHAR and value as JSON.

03 Under the interface

Durability beneath.
Independent reads above.

One writer and independent readers open the same durable dataset in object storage. Add a reader without giving it a separate full durable replica. Each reader keeps its own local cache.

GET uses SlateDB. SQL uses DuckDB over immutable Parquet published in the background. Both read paths are eventual; new readers need catch-up and cache warmup.
