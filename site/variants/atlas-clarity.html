FOR THE TEAM BUILDING THE APPLICATION

Clear boundaries.
Better application decisions.

The value is a contract your team can reason about. Durable acknowledgement, reader catch-up, and SQL publication each answer a different question.

01

Know the acknowledgement.

PUT and DELETE succeed after durable storage acknowledgement. A request ID correlates a response; it is not a durable deduplication key.

02

Keep uncertainty explicit.

A lost reply can leave a successful mutation unconfirmed. Unknown remains unknown, and the SDK does not automatically replay the mutation.

03

Observe the right read path.

A point GET and a SQL result can have different freshness. Poll the read your workflow actually needs instead of replaying a write.

Errors carry meaning.

These outcomes describe the attempt. They let your application preserve uncertainty rather than assume a failed mutation was rolled back.

OutcomeWhat is established
NotSentThis attempt did not send the mutation to the server.
RejectedA responding server confirms it did not apply this request.
UnknownThe mutation may have succeeded; the final result could not be established. No automatic replay.

THE TECHNICAL FOUNDATION

A system with
visible boundaries.

One writer, independent readers, and a background analytical projection explain why durable acknowledgement and read visibility are separate events.

Durable data stays in shared object storage. Readers fetch the same files and cache their working sets, without maintaining a full independent durable dataset copy per reader.

  1. PUT / DELETEOne writer persists through SlateDB and acknowledges durability. Writer and reader compute are separate.
  2. POINT GETSlateDB readers follow durable updates asynchronously. A lookup may still return an older value or a miss.
  3. SQL SELECTThe writer publishes a derived Parquet projection in the background. Readers run DuckDB over published files, without a fresh SlateDB table scan for each query.
Adding readers is an operator decision. Readers still need to load metadata, catch up, and warm caches. Read-serving capacity depends on the workload.

DEVELOPER PROOF / THE PUBLIC RUST SDK

Start the operation.
Keep the outcome.

The public Rust client handles byte CRUD, JSON tables, and SQL on one bounded multiplexed connection.

put generates a UUID and starts immediately. Use put_key for a caller ID or replacement, then get or delete by ID. JSON objects can have different and nested fields.

Raw byte PUT, GET, and DELETE remain available. Optional TTL applies to bytes and documents.

Run the example that polls for SQL visibility ↗
RockBeeClient / async Rust
use rockbee_client::{RockBeeClient, Result};
use serde_json::json;

async fn example() -> Result<()> {
    let client = RockBeeClient::connect("127.0.0.1:7100").await?;
    let products = client.table("products");
    let write = products.put(&json!({"name":"Keyboard"}));
    let id = write.id().to_owned();
    match write.await {
        Ok(_) => println!("durably acknowledged {id}"),
        Err(error) => {
            eprintln!("outcome={:?}: {error}", error.outcome());
            client.shutdown().await;
            return Err(error.into()); // Preserve uncertainty. No replay.
        }
    }
    let document = products.get(&id).await?; // Reader may lag.
    let result = products.query(
        "SELECT id, value->>'name' AS name FROM products"
    ).await?; // SQL publication may lag independently.
    println!("WAL {}: {:?}", result.exported_wal_file_id, result.rows);
    client.shutdown().await;
    Ok(())
}
Durable acknowledgement.
Successful PUT and DELETE mean SlateDB acknowledged durability. Point reads and SQL publication can still lag.
Explicit mutation outcomes.
Errors distinguish NotSent, Rejected, and Unknown. Uncertain mutations are never automatically replayed. Dropping an admitted eager PUT handle does not cancel it.
Visible expiry. Graceful completion.
TTL hides expired latest values in GET and SQL. Physical removal can happen later. Shutdown drains admitted work; optional CDC exports durable WAL changes.
