01 The useful separation

Add readers.
Keep the data in place.

Storage grows with your data. Compute follows the work. One writer and independent readers open the same durable dataset in object storage. A new reader shares that foundation instead of maintaining a separate full durable copy.

Readers have their own local caches. SlateDB serves key lookups; DuckDB runs SQL over an immutable Parquet projection published in the background. You choose reader compute separately from the storage it reads.

Catch-up and cache warmup still matter. GET and SQL are eventual; a durable write acknowledgement does not imply immediate reader visibility.

02 An explicit data path

Small interface.
Clear boundaries.

A Rust client for bytes and flexible JSON. Follow a write to its durable acknowledgement, then take either read path.

ILLUSTRATIVE SDK WALKTHROUGH

Write once.
Acknowledge durably.

Send a JSON object through RockBeeClient. The single writer persists the mutation through SlateDB before acknowledging it. Reader catch-up and Parquet export happen independently.

RUST / JSON TABLE
use rockbee_client::RockBeeClient;
use serde_json::json;

let client = RockBeeClient::connect(addr).await?;
let products = client.table("products");
let write = products.put(&json!({
    "name": "Field keyboard", "price": 129
}));
let id = write.id().to_owned();
write.await?; // durable acknowledgement

Generated UUIDs, caller-supplied IDs, optional TTL.
No automatic replay of uncertain mutations.

An independent reader.

GET routes through the gateway to a SlateDB reader. Its data cache lives in SlateDB. That reader can return an older value while it catches up with a recently acknowledged write.

// Reads the reader's current view.

Flexible documents.
Real DuckDB SQL.

The writer exports JSON tables to immutable Parquet objects in the shared store. Readers use DuckDB to query the published projection. SQL visibility follows export; it is separate from the durable ACK.

RUST / QUERY THE PUBLISHED TABLE
let result = products.query(
    "SELECT id, value
     FROM products
     WHERE TRY_CAST(
       value->>'price' AS DOUBLE
     ) < 150"
).await?;

// id is VARCHAR; value is JSON.
// Queries read published Parquet, not live writes.

A

One writer. Many read paths.

A single writer owns mutations for each storage prefix. Reader compute can be added independently against that shared dataset.

B

Structure when you need it.

Keep opaque keys and bytes, or use schema-free JSON tables. Documents can have different fields, with UUIDs or your own IDs.

C

Visibility, made explicit.

Durable acknowledgement, reader catch-up, and Parquet publication are distinct boundaries. Build for eventual reads.
