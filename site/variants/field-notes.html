01 / THE SYSTEMPersistence is shared.
Roles are separate.

Storage stays.
Compute can change.

Rockbee is disaggregated: the writer and readers provide compute, while shared object storage keeps the durable dataset. The gateway routes mutations to one writer and reads to independent readers. SlateDB’s WAL and SST files stay in object storage as serving processes come and go.

RockBeeClient → Gateway ─┬─ PUT / DELETE → Writer → SlateDB → object storage
                        │                    └─ background export → Parquet
                        └─ GET / SQL ──→ Readers → SlateDB / DuckDB

GET follows SlateDB updates. SQL reads published Parquet in shared object storage, including the S3-compatible local setup.

Add reader compute without maintaining a full independent durable dataset copy on every reader. Each reader loads metadata, catches up, and caches its working set from the shared files. Reader resources can be provisioned separately from the writer; the gateway keeps no key-value cache.

The writer maintains a derived analytical projection as Parquet in the same object store. DuckDB queries those published files, reusing the reader’s Parquet cache without a fresh SlateDB table scan per query. Point GETs follow SlateDB updates; SQL separately waits for Parquet publication. Both read paths are eventual.

02 / THE INTERFACEBytes when you want them.
Documents when you need them.

A common table.
Room for different fields.

A

Let documents differ.

Every document is a JSON object. A product with a price and another with an author can share a table. Nested objects and arrays stay in the original JSON.

B

Choose the identity.

put starts immediately and generates a UUID available before you await. Use put_key for your own ID or to replace a document. Read and delete by ID.

C

Keep your encoding.

Raw PUT, GET, and DELETE still accept opaque byte keys and values. JSON tables are another way into the same service, not a requirement for every value.

THE PUBLIC RUST CLIENT
use rockbee_client::{RockBeeClient, Result};
use serde_json::json;

async fn example() -> Result<()> {
    let client = RockBeeClient::connect("127.0.0.1:7100").await?;
    let products = client.table("products");
    let write = products.put(&json!({"name":"Keyboard", "price":99.5}));
    println!("submitted {}", write.id());
    let id = write.await?; // Durable acknowledgement.

    products.put_key("book-42", &json!({"author":"Alice"}), None).await?;
    let document = products.get(&id).await?; // Reader may still lag.
    let result = products.query(
        "SELECT id, value->>'name' AS name FROM products"
    ).await?; // SQL publication may still lag.
    println!("WAL {}: {:?}", result.exported_wal_file_id, result.rows);
    products.delete(&id).await?;
    client.shutdown().await;
    Ok(())
}

SQL sees id and value, the original JSON object. Select nested fields with DuckDB JSON expressions, or use filters and aggregates. The runnable example polls for SQL visibility.

03 / THE CONTRACTClear acknowledgements.
Explicit uncertainty.

Know what
has happened.

Durable is one milestone.
Successful PUT and DELETE mean SlateDB acknowledged durability. GET readers may still show an older value or a miss. SQL also waits for Parquet publication.
Unknown stays unknown.
Mutation errors distinguish NotSent, Rejected, and Unknown. An uncertain mutation is never automatically replayed. Dropping an eager PUT handle does not cancel its write.
Expiry is visibility.
Optional TTL applies to bytes and documents. GET and SQL hide an expired latest version without resurrecting its predecessor. Physical object deletion can happen later.
Changes can travel.
The optional rockbee-cdc tool exports durable WAL changes as JSON lines. Your consumer handles downstream delivery and duplicates; readers work without CDC.

An acknowledgement says the write is durable.
It does not say every reader has caught up.
