The architecture: separate compute, shared durable storage

01 / A DURABLE FOUNDATION. SEPARATE ROLES.
THE WHOLE SYSTEM

The writer and readers share durable object storage. Add reader compute without maintaining a full independent durable dataset copy per reader. Each reader still loads metadata, catches up, and warms its own cache.

ACTIVE LOCAL PILOTRust · SlateDB · DuckDBOne writer per prefix · Eventual reads
02 / THE OPERATING MODEL

Provision the work.
Keep the foundation.

Separate reader resources.

Writer and reader processes have different jobs. Reader compute can be provisioned independently as serving demand changes, against the same stored dataset.

Keep durable data shared.

Object storage holds SlateDB’s WAL and SST files. Readers cache their working sets, rather than each maintaining a full independent durable copy of the dataset.

Give SQL a projection.

The writer exports table data and durable changes into Parquet in the background. DuckDB queries that analytical projection, without a fresh SlateDB table scan per query.

03 / THE READ PATHS

Look up an ID.
Ask a question.

Point reads follow SlateDB. SQL follows published Parquet. Both are eventual, and a durable write does not mean either read path has caught up.

let products = client.table("products");
let document = products.get("keyboard-01").await?;

04 / THE PUBLIC RUST SDK

Bytes when you want.
JSON when you need.

Keep opaque byte keys and values, or select a JSON table. Objects can have different fields, including nested objects and arrays.

Table PUT starts immediately. Its generated UUID is available before you await the durable result. Use put_key for a caller ID or replacement; get and delete by ID.

Run the example that polls for SQL visibility ↗
RockBeeClient / async Rust
use rockbee_client::{RockBeeClient, Result};
use serde_json::json;

async fn example() -> Result<()> {
    let client = RockBeeClient::connect("127.0.0.1:7100").await?;
    let products = client.table("products");
    let write = products.put(&json!({"name":"Keyboard"}));
    println!("submitted {}", write.id());
    let id = write.await?; // Durable ACK.
    products.put_key("book-42", &json!({"author":"Alice"}), None).await?;
    let value = products.get(&id).await?; // Eventual.
    let result = products.query(
        "SELECT id, value->>'name' AS name FROM products"
    ).await?; // Publication may lag.
    println!("WAL {}: {:?}", result.exported_wal_file_id, result.rows);
    products.delete(&id).await?;
    client.shutdown().await;
    Ok(())
}
A durable acknowledgement.
Successful PUT and DELETE mean SlateDB acknowledged durability. Mutation errors distinguish NotSent, Rejected, and Unknown. Uncertain mutations are never automatically replayed.
A bounded client lifecycle.
The SDK multiplexes requests on a shared connection. Dropping an admitted eager PUT handle does not cancel the operation. Shutdown drains admitted work.
An optional lifetime.
TTL applies to bytes and JSON. GET and SQL hide expired latest values. Physical object removal can happen later. Optional CDC exports durable WAL changes as JSON lines.
