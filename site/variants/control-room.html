Provision readers for traffic.

Configure another reader against the same storage prefix as serving demand changes. The durable dataset stays in shared object storage.

Cache hot data. Share the full dataset.

A reader does not need its own independent full durable replica. It keeps a local cache and fetches data from the shared store when needed.

Keep the read paths explicit.

GET uses a SlateDB reader. SQL uses DuckDB over the immutable Parquet projection published in the background. Both paths are eventual.

New readers need catch-up and cache warmup. Cold reads use object storage; throughput and cost depend on the workload.

Success means durable.

PUT and DELETE are acknowledged after SlateDB confirms durability. The writer does not wait for Parquet publication. If a mutation's outcome is uncertain, Rockbee does not automatically replay it.

⇢

Visibility is eventual.

Readers follow independently. SQL adds a second asynchronous boundary: published Parquet. Query results include an exported WAL watermark, so the published position is explicit.

RUST / RockBeeClient
use rockbee_client::RockBeeClient;
use serde_json::json;

let client = RockBeeClient::connect(
    "127.0.0.1:7000"
).await?;
let products = client.table("products");

// Generate an ID. Await durable completion.
let id = products.put(&json!({
    "name": "Field keyboard", "price": 129
})).await?;

// Or supply an ID; each document can differ.
products.put_key("studio-lamp", &json!({
    "name": "Studio lamp", "color": "sage"
}), None).await?;

let rows = products.query(
    "SELECT id, value FROM products"
).await?;
Generated UUIDs are available on the PUT handle before awaiting completion.
