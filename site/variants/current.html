01 / Different jobs. Different lifecycles.

Another reader.
The same
durable data.

Rockbee separates compute from storage. Add reader processes against the shared object store without creating a full independent durable dataset replica for every reader.

AKeep objects shared.

Persisted data lives in object storage such as S3, separate from individual reader process lifecycles. Each reader still needs its own memory, caches, and catch-up work.

BGive each request a path.

The gateway sends mutations to the single writer and reads to readers. Point GETs use SlateDB. SQL uses reader-side DuckDB over background-published Parquet.

CLet the projection catch up.

A durable write does not mean immediate reader visibility. SQL publication is a separate eventual step. Results include the exported WAL watermark.

Your data.
Three ways in.

Keep the raw byte API when you want control of encoding. Pick JSON tables when you want documents and SQL. One Rust client handles both.

01

BYTES

Opaque keys and values. PUT, GET, DELETE. KV caching lives in SlateDB, without a separate gateway data cache.

key: &[u8], value: &[u8]
02

OBJECTS

Schema-free JSON. Different fields in different records. Generated UUIDs or caller-owned IDs, replacement writes, and optional TTL.

{"name":"Keyboard"}
03

SQL

Actual DuckDB SELECTs: projections, JSON functions, ordering, and aggregates over a background Parquet projection.

value->>'name'

MAKE
A MOVE.

Connect with RockBeeClient. Choose a table. Write a JSON object, or ask a question in SQL.

Eager handles expose the generated UUID before you await a durable write. Use put_key when the ID is already yours.

Open the complete example ↗
use rockbee_client::RockBeeClient;
use serde_json::json;

let client = RockBeeClient::connect(&gateway).await?;
let products = client.table("products");

let write = products.put(&json!({"name": "Keyboard"}));
println!("{}", write.id()); // UUID, before await.
let id = write.await?;     // Durable acknowledgement.

products.put_key("sku-42", &json!({"name": "Keyboard"}), None).await?;
let document = products.get("sku-42").await?;
products.delete(&id).await?;
Illustrative async Rust excerpt. Reader GET and SQL visibility are eventual.
02 / Clear expectations

Know what comes back.

DURABILITY

Success waits for storage.

PUT and DELETE return success after SlateDB’s durable acknowledgement. Submission and waiting are separate with eager completion handles.

VISIBILITY

Readers need to catch up.

A reader may lag the writer. SQL can lag a point GET while the exporter publishes Parquet. An ACK is not immediate read-after-write visibility.

UNCERTAINTY

No automatic mutation replay.

A lost acknowledgement can leave an unknown outcome. Rockbee makes that explicit. Your application chooses the recovery policy.
