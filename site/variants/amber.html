SMALL INTERFACE. MORE WAYS IN.

Keep it simple.
Keep your options.

Use bytes for an encoding you already own. Use JSON tables for flexible documents. Ask SQL questions over published data.

01

Bytes, without ceremony.

Opaque, nonempty byte keys and values. PUT, GET, and DELETE through the same public client. Your application chooses the encoding.

02

Documents, without a fixed shape.

A price here, an author there. Store different JSON object fields in one table. Get, replace, or delete a document by its generated UUID or your own ID.

03

SQL, with a real engine.

DuckDB SELECT over Parquet, with filters, projections, and aggregates. SQL exposes id and the original JSON value. Results contain JSON rows and a published WAL watermark.

04

A lifetime, when you need one.

Optional TTL for bytes and documents. Readers hide expired latest versions; SQL does too. Expiry changes visibility before physical storage is necessarily reclaimed.

DISAGGREGATED BY DESIGN.

One writer.
Independent readers.
One durable dataset.

Compute and durable storage live separately. One writer and independent readers share the same object-store dataset. The gateway routes PUT and DELETE to the writer, and GET and SQL to readers.

Add readers without maintaining a full independent durable dataset copy for each one. Readers fetch shared files and build their own caches. Provision reader compute separately from the writer; new readers still need to catch up and warm up.

GET: SlateDB reader catch-up.
SQL: background Parquet publication + DuckDB.
Both are eventual. A durable ACK is not immediate visibility.

  1. 01 / WRITE

    Make the change durable.

    SlateDB persists the writer’s changes to shared WAL and SST files in object storage, then acknowledges durability.

  2. 02 / PREPARE IN THE BACKGROUND

    Give SQL its own read path.

    The writer maintains a derived Parquet analytical projection in the same object storage. Publication happens in the background after durable table changes.

  3. 03 / READ

    Look up. Or ask.

    Point GETs use SlateDB. SQL uses DuckDB over published Parquet, reusing the reader’s file cache without a fresh SlateDB table scan per query. The gateway keeps no key-value cache.

THE PUBLIC ASYNC RUST CLIENT

Write now.
Await the answer.

RockBeeClient shares a bounded, multiplexed connection. Table PUTs are eager: the generated ID is ready before you await the durable result.

Reader visibility and SQL publication can lag. Poll reads when you need to observe a change; an uncertain write is never automatically replayed.

Run the complete polling example ↗
main.rs / RockBeeClient
use rockbee_client::{RockBeeClient, Result};
use serde_json::json;

async fn example() -> Result<()> {
    let client = RockBeeClient::connect("127.0.0.1:7100").await?;
    let products = client.table("products");
    let write = products.put(&json!({"name":"Keyboard"}));
    println!("submitted {}", write.id());
    let id = write.await?; // Durable ACK.

    products.put_key("book-42", &json!({"author":"Alice"}), None).await?;
    let value = products.get(&id).await?; // Eventual.
    let result = products.query(
        "SELECT id, value->>'name' AS name FROM products"
    ).await?; // Publication can still lag.
    println!("WAL {}: {:?}", result.exported_wal_file_id, result.rows);
    products.delete(&id).await?;
    client.shutdown().await;
    Ok(())
}
THE ACKNOWLEDGEMENT
Durable means persisted.
PUT and DELETE succeed after SlateDB’s durable acknowledgement. A lost reply can still mean a successful mutation; errors report NotSent, Rejected, or Unknown.
THE COMPLETION HANDLE
Dropped does not mean canceled.
An admitted eager PUT keeps running if its handle is dropped. Shutdown drains admitted work. Uncertain mutations are never automatically replayed.
THE OPTIONAL CHANGE FEED
Take changes somewhere else.
rockbee-cdc exports durable WAL changes as JSON lines. Your consumer handles duplicates and downstream delivery. Readers need no CDC process.
