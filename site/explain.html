03 / THE ARCHITECTURAL CHOICE

Compute comes and goes.
Durable data stays.

SlateDB keeps the durable database in object storage. Rockbee readers open that shared data and build their own working caches. SQL adds a separate Parquet representation.

A

The authoritative KV store

SlateDB manages WAL files, sorted string tables, and metadata. The writer waits for durability before a successful mutation acknowledgement.

PARQUET SEGMENTS + MANIFESTS

Each process has SlateDB caches. Each SQL reader also caches Parquet in local temporary files. Replacing a reader loses warmth, not authoritative data.

What this buys you

Reader capacity can grow without provisioning a complete durable database copy per reader. You still pay for compute, caches, object requests, transfers, and cold-start work. Operators provision the readers; the system does not automatically scale them.

04 / WHERE OTHER DESIGNS GET EXPENSIVE

Every database
sends you a bill.

Sometimes it is RAM. Sometimes it is replica storage, rebalancing, or operational work. The useful question is which tradeoff your application can afford.

Redis OSS

Self-managed Redis Open Source with RDB / AOF persistence. Redis Cloud and Redis Software have different operating models.

RAM is a great place for a hot working set. Keeping an entire growing dataset there changes the economics.

WHERE IT CAN HURT

  1. Memory is a capacity decision. Keys, values, and data-structure overhead consume RAM. Redis recommends provisioning for peak memory; persistence does not turn the live dataset into an object-store working set.
  2. Durability has knobs. RDB snapshots can lose changes since the last snapshot. AOF improves recovery freshness, with log growth, rewrites, and replay to manage.
  3. Background work still costs resources. Snapshotting and AOF rewriting use fork and copy-on-write. Large, write-heavy datasets need memory headroom and latency monitoring.

WHY YOU MIGHT STILL CHOOSE IT

  • Rich in-memory data structures for counters, queues, sets, and hot application state.
  • Real persistence options: RDB, AOF, or both. Redis is much more than a disposable cache.

What Rockbee changes

Durable data lives in shared object storage; readers cache their working sets. The cost is eventual reader visibility and cold object fetches. Rockbee does not provide Redis’s data structures or promise its in-memory latency.

Redis: memory allocation ↗Redis: persistence tradeoffs ↗

Couchbase Server

Self-managed Couchbase Server, including Enterprise Magma. Capella and other managed Couchbase offerings are separate comparisons.

A broad distributed database gives you more capabilities—and more service placement and capacity decisions.

WHERE IT CAN HURT

  1. The service topology is yours to manage. Data, Query, Index, Search, and other services have their own placement and resource needs. A SQL++ query can involve several roles.
  2. Growth can involve rebalancing. Adding or removing nodes and changing service placement can redistribute data and indexes. Capacity changes are cluster operations to plan and monitor.
  3. Disk-oriented still needs sizing. Magma supports datasets larger than memory, but storage hardware, memory quotas, flushing, and compaction remain part of the operating model.

WHY YOU MIGHT STILL CHOOSE IT

  • Multi-Dimensional Scaling already separates services so Data, Query, Index, and Search can scale independently.
  • SQL++, indexing, search, and a disk-oriented storage engine provide a broader document-database toolkit.

What Rockbee changes

A smaller topology: one writer, independent readers, and shared durable objects. You give up Couchbase’s broader indexing and service ecosystem. Rockbee’s SELECT-over-Parquet path is a different query contract.

Couchbase: services & MDS ↗Couchbase: Magma ↗Couchbase: rebalance ↗

PostgreSQL

PostgreSQL 18 with conventional physical primary / standby replication. Managed services and shared-storage variants can differ.

Read replicas bring more serving capacity. They also bring database copies, WAL replay, and another recovery path.

WHERE IT CAN HURT

  1. A physical standby starts from a database copy. Each maintains its own data directory and applies the primary’s WAL. More replicas mean more storage and replay work.
  2. Lag and durability are explicit choices. Asynchronous replicas can lag and lose recent commits on failover. Synchronous replication waits for selected standbys and adds commit latency.
  3. WAL retention needs attention. Slots protect lagging replicas, but retained WAL can fill storage. A replica that falls behind available history can require a new base backup.

WHY YOU MIGHT STILL CHOOSE IT

  • ACID transactions, constraints, indexes, joins, and a mature relational SQL ecosystem.
  • With configured synchronous standbys, synchronous_commit = remote_apply waits until changes are applied and visible there.

What Rockbee changes

Readers use shared durable objects instead of maintaining a complete durable replica. Rockbee trades away multi-key transactions, immediate reader freshness, and automatic writer failover. A transactional system of record may still belong in PostgreSQL.

PostgreSQL: physical & synchronous replication ↗PostgreSQL: availability choices ↗PostgreSQL: transactions ↗PostgreSQL: commit settings ↗
Rockbee’s bet: durable data belongs in shared storage.

Choose it when byte-key lookups, flexible JSON, and an eventually published SQL view fit the workload. A single writer, eventual reads, and bounded single-table queries are part of that choice. Checkout transactions and strict read-after-write requirements call for a different contract.

THE SOURCE OF TRUTH

Rust services.
Embedded engines.

Rockbee is written in Rust. SlateDB owns durable KV storage. The Rust DuckDB crate embeds the native DuckDB engine for Parquet export and SQL.

DuckDB is an embedded library in the writer and reader processes; there is no separate DuckDB server.

The public client: KV by default, tables when you need them

RockBeeClient exposes put, get, and delete for nonempty opaque byte keys and values. User keys are limited to 65,534 bytes; the complete wire frame must also fit its 1 MiB bound. client.table("products") creates a JSON-table handle sharing the same connection, admission limits, and shutdown lifecycle. It uses composition, not inheritance.

use rockbee_client::RockBeeClient;
use serde_json::json;

let client = RockBeeClient::connect("127.0.0.1:7100").await?;

// Byte values: the application chooses the encoding.
client.put(b"cart:customer-42", b"product-42:2", None).await?;
let cart = client.get(b"cart:customer-42").await?;

// JSON table: generate a UUID, or choose your own ID.
let products = client.table("products");
let id = products.put(&json!({
    "name": "Trail Backpack", "price": 79
})).await?;
let product = products.get(&id).await?;
// Either GET can lag a preceding durable PUT.

put_key(id, document, ttl) replaces a document under a supplied ID. JSON objects can have different fields. Raw keys and table IDs live in separate physical namespaces.

What a successful PUT means, and what a lost reply means

A PUT starts eagerly and returns a completion handle. Dropping an admitted handle does not cancel the write. Awaiting success confirms that the writer acknowledged SlateDB durability. Shutdown drains admitted operations, including dropped handles, before disconnecting.

OutcomeWhat the application knows
NotSentThe client did not enqueue the request.
RejectedA server response confirms the mutation was not applied.
UnknownThe mutation may have become durable. A lost reply cannot settle that question.

The client and gateway do not automatically replay uncertain mutations. Request IDs correlate responses on a connection; they are not durable deduplication keys. By default, client clones share 128 active and 128 pending slots, with a 5-second end-to-end request deadline.

On the wire: Protobuf messages over bounded TCP connections

proto/rockbee.proto defines the versioned envelope, requests, responses, and correlation IDs. Prost generates Rust types; the generated file is checked into the repository and included by the protocol crate. Ordinary Cargo builds use that file. Regeneration is an explicit developer command.

4-byte big-endian length | Protobuf Envelope
                          version = 1
                          request_id = positive integer
                          oneof: KV / Table / Status / Response

Maximum frame: 1 MiB, including the length prefix.

This is a custom TCP protocol. Multiplexed requests use positive IDs; zero is reserved for sequential mode. The shared RPC layer bounds connections and in-flight work. Its frame read/write timeouts are separate from client and query execution deadlines.

cargo run -p rockbee-protocol --example generate_protocol

Gateway routing, reader refresh, and caches

Validated mutations take the one writer route exactly once. GET and SQL requests go to readers in round-robin order, with reader failover inside one routing budget. A successful missing-value response is final; the gateway does not ask another reader to search for a newer value.

Readers use SlateDB’s read-only DbReader, replay WAL data, and refresh their view. The checked-in poll interval is 10 seconds. That is a polling setting, not a visibility guarantee. Lower intervals trade extra object-store requests for more frequent refresh.

The gateway has no separate KV cache. Each writer or reader has SlateDB block and metadata caches; SQL adds a reader-local Parquet file cache. Cold requests can fetch durable objects, while warm requests may use the working set already present.

A table is a separate JSON namespace, not a different database

Rockbee keeps opaque byte keys and JSON tables in the same SlateDB database, under disjoint physical key prefixes. A table name is an ASCII identifier of 1–64 bytes; a document ID is UTF-8 and may be up to 1,024 bytes. A table value must be a JSON object. A table PUT writes the document and a durable catalogue entry in one SlateDB batch, so the exporter can discover the table after a restart.

raw key       = [0, ...]
table prefix  = [1, table_name_length, ...table_name_bytes]
catalogue key = [2, ...table_name_bytes]

Export objects are deliberately outside the SlateDB data paths. The table name is hex encoded, preserving distinct case-sensitive names even when the object store is a local filesystem.

<prefix>/_rockbee_tables/<hex-table-name>/
  segments/<uuid>.parquet
  manifests/<20-digit-revision>.json

Export starts with a pinned snapshot, then follows the WAL

A writer-owned background worker checks registered tables every 500 ms. A table’s first export, a compaction, or a detected WAL gap builds a new base generation. This work is independent of the mutation acknowledgement: the client receives success only after SlateDB durability, not after Parquet publication.

  1. Flush the writer memtable and create a detached SlateDB checkpoint with a 24-hour lease.
  2. Scan that pinned checkpoint for the current rows of one table, writing bounded Parquet batches.
  3. Record the checkpoint’s WAL high-water mark, then consume the committed WAL tail through EOF.
  4. Publish the complete generation only after all of its segments exist.
Export boundValue
Batch before encoding1,000 rows or approximately 8 MiB
Encoded Parquet segment32 MiB maximum

The manifest cursor is exported_wal_file_id. It advances only after a whole WAL file has reached EOF; uploaded partial batches are not made visible on their own. A missing/truncated WAL causes a fresh pinned snapshot rather than skipping history.

Immutable segments become visible through a manifest revision

Each Parquet row contains the document ID and JSON value plus the ordering and visibility metadata needed to reconstruct current table state: seq, absolute expiry, tombstone, WAL file ID, and row ordinal. Segment writes use create-only object-store operations. Only afterwards can the worker publish a new create-only manifest revision.

Publication checks the active SlateDB writer epoch, requires the expected preceding revision, and rejects a cursor that would regress. The result is a complete immutable generation or the preceding published generation; a failed upload or publication does not make partial state queryable.

SQL reads local cached Parquet, then reconstructs the latest document

A reader reloads the table manifest for every SQL query. It checks that every referenced segment stays inside that table’s object prefix, downloads any cache miss into a reader-owned temporary directory, verifies its manifest size, and gives DuckDB those local file paths. DuckDB does not directly read S3 or SlateDB for a query.

Before your SQL predicates run, Rockbee builds the selected table view by selecting the newest row for each id. The ordering is exact:

row_number() OVER (
  PARTITION BY id
  ORDER BY seq DESC, wal_file_id DESC, row_ordinal DESC
)

Only rank 1 remains; then its tombstone and expiry are evaluated. This ordering matters: an older live value cannot reappear when the newest record is a delete or has expired.

manifest reload and execution · local download cache · deduplication and visibility view

Deletes and TTL use the same newest-record rule

A table delete is a durable SlateDB tombstone. The exporter preserves it as a Parquet row with tombstone: true; queries remove it only after deciding that it is the newest row for that ID. This keeps a historical pre-delete value from resurfacing.

TTL is stored as an absolute Unix-millisecond expiry. ttl_millis = 0 means no expiry. At the exact expiry instant a point read is invisible, and query SQL uses the equivalent condition expires_at_unix_ms > now. A later non-expiring PUT replaces an earlier expiry because it is the newest record.

ttl_millis == 0  // Ttl::NoExpiry
ttl_millis > 0   // Ttl::ExpireAtMillis(now + ttl_millis)

table TTL and delete durability · wall-clock TTL semantics · tombstone export

Query execution is deliberately bounded and single-table

Each query gets an in-memory DuckDB connection and a private spill directory. External access, persistent secrets, and extension auto-loading are disabled. SQL must be one SELECT; DuckDB parses it into a syntax tree, and Rockbee permits only the selected unqualified table and lexical CTEs. Expressions, joins over CTEs, and aggregates still run in DuckDB. Allowed table functions are range, generate_series, unnest, json_each, and json_tree; file scans, other tables, and catalogue access are rejected.

Recovery favors a known published generation over a speculative one

On writer restart, Rockbee detects registered tables and restarts export even without another mutation. The exporter retries transient object-store failures, but a newer SlateDB writer epoch fences the old exporter. On normal shutdown it cancels and joins the exporter before closing the database; owned checkpoint cleanup is attempted on completion, failure, and cancellation.

Compaction creates a new snapshot generation after at least 128 delta segments and 60 seconds. It replaces what the current manifest references, preserving the same visibility rules. Manifest revisions and unreferenced Parquet objects are currently retained; automatic garbage collection is not implemented.

SQL is eventually consistent with durable writes. A registered table with no first manifest returns a warming error. A lagging reader may not yet see the catalogue entry and can treat the table as empty. The returned exported_wal_file_id describes the export generation used; it is not a write receipt or a cross-reader read barrier.

What SQL returns to the application

The selected table exposes id VARCHAR and value JSON. Your SELECT shapes each result row. SQL reads the published projection, so this example result applies after the product is visible in that generation.

let result = products.query(
    "SELECT id, value->>'name' AS name,
            TRY_CAST(value->>'price' AS DOUBLE) AS price
     FROM products
     WHERE TRY_CAST(value->>'price' AS DOUBLE) < 100
     ORDER BY price"
).await?;

for row in result.rows {
    println!("{row}");
}

CDC, restarts, and operating the processes

rockbee-cdc tails durable SlateDB WAL changes into JSON lines. It flushes output before advancing a locked, source-bound cursor. Crashes may repeat events, so consumers need at-least-once handling. TTL expiry does not emit a delete event; engine-private table and catalogue keys are filtered from this raw KV stream.

make local starts an owned writer, reader, and gateway on dynamic ports with a unique storage prefix. It prints connection details. Fixed development configs use gateway 7100, writer 7101, and reader 7102. Start the writer before the reader.

--check-config reports effective configuration without proving connectivity. A status probe reports endpoint role and local RPC counters; it does not prove storage health or reader freshness.

Reader request failover is implemented. Automatic writer failover and write sharding are not. The public transport is plain TCP without built-in authentication or TLS; deployments must supply the required network boundary. SQL path restrictions are not a tenant-authentication system.
