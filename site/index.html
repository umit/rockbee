let cart_key = b"cart:customer-42";

// Save the cart for 30 minutes.
client.put(
    cart_key,
    br#"{"items":[{"sku":"keyboard-01","quantity":2}]}"#,
    Some(std::time::Duration::from_secs(30 * 60)),
).await?;

// Load it when the customer returns.
// A recent write may not be visible to the reader yet.
let cart_bytes = client.get(cart_key).await?;

// After checkout is complete, remove the saved cart.
client.delete(cart_key).await?;
GET returns the stored bytes, or None when no cart is visible. Your application decodes the JSON. PUT and DELETE await durable acknowledgements; reader visibility is eventual.
WRITE ONCE / TWO WAYS TO READ

From a document
to an answer.

Start with a JSON product. Fetch the document by ID, or ask a question across the table with SQL.

  1. Put the document.

    put starts the write and generates a UUID. Awaiting its handle returns that ID after a durable acknowledgement.

  2. Get it by ID.

    get(&id) returns the original JSON object from a reader. A new write can return None until that reader catches up.

  3. Query the table.

    query(sql) runs your SELECT in DuckDB on a reader. This example finds products under 100 and returns only name and price, ordered by price.

GET / DOCUMENT ONCE VISIBLE
{
  "name": "Keyboard",
  "price": 99.5,
  "brand": "Logitech"
}

The SELECT aliases become JSON keys. brand stays in the stored document; this query does not select it. Other matching products produce more rows.

catalog.rs · put → get → query
use serde_json::json;

let products = client.table("products");

// 1. Write JSON. Await a durable acknowledgement.
let write = products.put(&json!({
    "name": "Keyboard",
    "price": 99.5,
    "brand": "Logitech"
}));
let id = write.await?;

// 2. Read the original document by ID.
// May be None until the reader catches up.
let document = products.get(&id).await?;

// 3. Query the published table with real SQL.
// The latest write may not be published yet.
let result = products.query(
    "SELECT value->>'name' AS name,
            TRY_CAST(value->>'price' AS DOUBLE) AS price
     FROM products
     WHERE TRY_CAST(value->>'price' AS DOUBLE) < 100
     ORDER BY price"
).await?;

println!("{}", serde_json::to_string(&result.rows)?);
EXAMPLE RESULTresult.rows · after publication
[
  {
    "name": "Keyboard",
    "price": 99.5
  }
]
value holds the stored JSON. ->> extracts a field as text; TRY_CAST converts price to a number for filtering and sorting. Each selected row becomes a JSON object in result.rows.
Durable now. Query-visible after publication.

The writer publishes Parquet in the background. A query made immediately after PUT can see older data or report that the table is warming up. If you need this new record, retry the read/query with a deadline; never replay an uncertain write. The full SDK example shows bounded polling.

03 / THE FOUNDATION

Independent compute.
Shared durable storage.

Compute serves requests. Object storage keeps durable data. This is disaggregated architecture: size readers for traffic and storage for the dataset, without a full durable database copy for every reader.

01 Gateway
Your client connects here. It sends PUT and DELETE to the writer, and GET and SQL to readers.
02 One writer
Owns mutations for a storage prefix. SlateDB makes writes durable. The writer also uses DuckDB to export JSON table data into Parquet in the background.
03 Independent readers
Serve lookups and queries with their own compute and local caches. Add reader processes as read demand grows.
04 Object storage
Holds shared durable files: SlateDB write logs and data files, plus the Parquet projection used for SQL.

01 / BACKGROUND PUBLICATION

Writer prepares the data.

Writer / DuckDB → Parquet → Object storage

The writer's export worker uses DuckDB to turn table data into Parquet files and publishes them in object storage. This runs separately from the durable PUT acknowledgement.

02 / WHEN YOU CALL QUERY

Reader answers the question.

Gateway → Reader / DuckDB → JSON rows

The gateway sends your SELECT to a reader. Its DuckDB engine reads the published Parquet projection and returns the selected columns. It does not wait for a fresh export on each query.

WRITE → DURABLE ACK

Client → gateway → writer. SlateDB persists the mutation in object storage before the writer acknowledges success. Readers catch up independently; the writer publishes the SQL projection in the background.

WHAT THIS MEANS IN PRACTICE

More read traffic? Add reader compute.

Configure another reader against the same storage prefix and include it in the gateway's reader list. It opens the shared dataset and warms its own cache. You do not need a full durable replica for every reader, and adding a reader does not require increasing writer compute.

Reader provisioning is explicit. Catch-up and cache warmup take time; capacity depends on your workload and the rest of the system.

GET / THE ORIGINAL VALUE

SlateDB serves the key.

A reader looks up the byte key or document ID through SlateDB. Its local cache keeps frequently used data close; shared object storage supplies the durable files. Readers follow the writer's updates, so a recent write may not be visible immediately.

Explore the reader ↗
SQL / WRITER + READER

Writer publishes. Reader queries.

DuckDB has a job on both sides. The writer uses it to create Parquet files from JSON table data and publishes those files asynchronously. On a reader, DuckDB runs your SELECT over the published projection and returns JSON rows. The export and the query are separate operations.

05 / THE CONTRACT

Simple to use.
Clear about behavior.

Durable writes.
A successful mutation means SlateDB acknowledged durability. The client exposes uncertain outcomes and never automatically replays uncertain writes.
Eventual reads.
GET follows reader catch-up. SQL follows Parquet publication. A successful write can take time to appear on either read path.
Bounded SQL.
Reader query memory, concurrency, and timeouts are configurable. Results have explicit row and byte limits.

A FEW GOOD QUESTIONS

Before you build.

Is this a key-value store or a SQL database?+

The core stores opaque byte keys and values. JSON tables add document IDs and real DuckDB SELECT queries over a derived Parquet projection. SQL reads JSON tables; it does not interpret arbitrary byte values.

What does scaling mean here?+

Reader processes share durable storage and can be provisioned separately from the writer. There is one writer per prefix. Operators configure readers; automatic scaling, sharding, and automatic writer failover are outside the current scope. Capacity depends on the workload, caches, gateway, network, and object store.

Why object storage?+

Durable data lives independently of serving processes. Readers fetch shared files and cache their working sets locally, so each reader does not need a full independent durable replica. Cold reads, object requests, transfer costs, and cache warmup remain part of the design.

What should I evaluate first?+

Start with a product catalog, application content, or saved model outputs where eventual reads fit the workflow. Run a writer and reader against your object store, then measure lookup latency, SQL publication lag, and recovery with your own data. The setup guide walks through the full path.
