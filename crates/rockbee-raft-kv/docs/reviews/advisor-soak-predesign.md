# Stable three-node soak and subsequent communication review

Predesign approved by advisor and verifier. This is an implementation/test gate, not a claim that the soak has run. No production edits or builds by advisor. Node movement is not automatically the next task.

```text
public Client clones -> one in-process Gateway -> three owned CLI nodes
                         stable topology; no injected faults
```

Use an opt-in ignored Rust integration test with bounded duration and worker count. Reuse exact owned child handles and isolated temporary databases from `ProcessCluster`. Complete real metadata and all four data-group readiness checks and an excluded warmup before releasing one common measurement barrier. Each worker owns disjoint keys; its 1 KiB values encode worker/iteration/version so stale values remain distinguishable. Run sequential committed PUT, exact GET, committed update, exact GET, committed DELETE, GET absence. Never hide a mismatch with polling. A failed or uncertain mutation stops dependent steps; do not replay it. Count NotSent, Rejected, Unknown and read failures separately and mark the stable validation run unsuccessful when an unexpected outcome occurs.

Measure each mutation from before eager submission, including admission. Report six successful operations per completed cycle, cycles, errors and partial cycles separately. Use monotonic elapsed time from the barrier through the last counted completion, including bounded draining, or explicitly exclude and separately report tail completions. Do not divide extra tail completions by only the configured duration. Report per-operation latency distributions so strong reads and durable writes are distinguishable. The user explicitly selected the mature `hdrhistogram` library: root added exact version 7.6.0 as a node dev dependency with default features disabled. Use configured finite bounds/precision and explicit out-of-range accounting; never silently drop or clamp an outlier into a misleading percentile. Include actual duration, concurrency, payload, topology, warmup and histogram resolution in the result. This is warm closed-loop observed throughput, not maximum capacity or an open-loop latency claim.

Register signals before launching children. Unlike the old direct scenario-drop cleanup, a soak with spawned workers must retain its owning scope on a signal: stop new cycles, drain ongoing operations within configured deadlines, join workers, then close the client/gateway and stop/drop exact children. If a drain deadline forces cancellation, abort and join every worker before closing shared resources; mark the run canceled. Parent SIGKILL/abort still cannot execute Rust cleanup. Keep the existing external-owner fallback limitation explicit.

Focused fixture gates suffice: invalid/overflowing configuration rejected before spawn; our sample/count/merge/report and out-of-range accounting with fixed synthetic observations; exact operation/error accounting for a failed mutation; a short real three-node smoke run; and controlled signal cancellation during active workers proving worker completion precedes child/storage cleanup. Do not test HDR internals or implement a replacement histogram. Avoid a second benchmark framework or unbounded latency vectors.

## Evidence-based communication priorities after the soak

1. **Response-writer termination must retire intake.** Current `transport/server/runtime.rs::run_connection` selects stop, handler completion and input, but does not observe its writer task exiting on an output error/timeout. A peer that continues sending can therefore trigger new handlers after output is known unusable. Reproduce a slow/nonreading output with continuing input and assert that writer completion stops new admission while already accepted handlers remain owned and drain. A small writer-completion branch in the existing pinned-receive loop is the likely repair; establish the regression first. Both reviewers agree this is a concrete next communication issue, not a blocker for the first no-fault soak.
2. Exercise slow-reader and repeated connection/drop/close behavior through actual sockets with exact handler/permit accounting. Verify bounded retained work and return to baseline after all accepted work resolves. Existing Link tests already cover handoff certainty, stale timers, duplicate/unknown responses, partial writes, dropped handles and held receive reservations; do not reproduce the same cases without new real-path evidence.
3. Add a real public-path response-loss case with explicit dispatch/proposal instrumentation. Preserve Unknown without automatic mutation replay; a later fresh request is separate work. Backend fixture dispatch counts alone do not prove the number of Raft proposals or durable applications.
4. Let soak results select the next performance or durability test. Persistent peer connections, batching changes, allocator/runtime settings and node churn require evidence before changing behavior. Keep repeated movement and general membership management visibly unfinished until separately scheduled.
