# Task 7 first-move design challenge

Root explicitly authorizes the bounded first implementation: one immutable move target per data group, demonstrating ABC -> ABD. This is not approval or completion of a general move manager with successive epochs. Later different moves remain pending. No production edits or Cargo commands in this review.

## Source-backed boundary

Cached OpenRaft 0.9.25 `raft/impl_raft_blocking_write.rs::change_membership` submits the same `ChangeMembers` twice: first joint, then uniform. The core computes each change against its current membership. `membership/membership.rs::next_coherent` progresses ABC toward ABD through joint membership and leaves ABD at ABD when the same target repeats. `add_learner(D)` uses AddNodes, which neither changes voters nor replaces D's existing endpoint. Thus delayed add-D/change-to-ABD work cannot restore C if every accepted job, endpoint and emitted membership operation has the same immutable intent. Do not expose arbitrary voter sets or rollback phases through a raw control RPC.

This proof does not extend to a different later target. Checking an application epoch and subsequently calling public `change_membership` is still a TOCTOU gap. General successor jobs need proven retirement/drain of all prior executors or a separately reviewed conditional consensus integration. A leader-local mutex is not that proof.

Persist the first job and its immutable ID, group, original voters, target voters and D endpoint. Same ID/same intent reconciles; same ID/different intent rejects. A new ID must not overwrite the existing job even when it names the same target. Conflict rejection must survive restart. Root selected explicit D join mode rather than requiring a predeclared spare: D's local endpoint is separate from the initial ABC directory, and a linearizable seed metadata read validates cluster/hash identity. This remains a bounded fourth-node join, not arbitrary endpoint replacement.

## Required ordering and observations

- Replace bootstrap's ordinary Put emission with apply-time initialize-if-absent before mutable metadata. Add small conditional metadata transitions with expected revision/job/phase and small Applied/Conflict responses. Two conditional entries in one WriteBatch must observe each other's accepted transition, rather than both reading the pre-batch DB value. A typed per-chunk state or isolated conditional chunks suffices; no general transaction framework is needed. Preserve existing Put/Delete persisted tags and valid historical bootstrap-log replay to a new learner.
- Stored-directory validation must permit compatible later revisions, checking cluster/hash/shape rather than requiring exact equality to initial configuration. D starts the same group identity uninitialized; it must never initialize an independent copy of the group or group zero. Reopen preserves received durable group state and validates stored node identity. BeginMove records D's endpoint in the immutable job; publication adds it to the catalog only after final membership proof. Validate endpoint/ID consistency against both the published catalog and every persisted job, so concurrent jobs cannot assign the same D ID different endpoints. Bound the union of prospective catalog IDs, not just the published directory; same ID/same endpoint may serve multiple group moves.
- `add_learner(blocking=true)` is not sufficient catch-up proof: `raft/mod.rs::check_replication_upto_date` treats leader loss and removed learner as completion; the wrapper returns its old response. Obtain a fresh authority barrier and same-leader replication evidence that D matched at least its captured LogId. Clear/recompute that evidence on leader/vote change. D is still a learner and cannot count in the old quorum.
- Reconcile actual committed/applied membership after uncertainty. `metrics.membership_config` can represent effective, uncommitted membership. Use a coherent applied StateRecord covering a fresh barrier, or a source-verified committed-state API. A returned final membership success is useful evidence; a cached hint or effective joint configuration is not a publication proof.
- Branch on that actual membership: old uniform ABC requires learner/catch-up before first promotion; joint ABC/ABD needs same-target finalization; uniform ABD goes directly to final proof/publication. A resumed controller on leader D must not wait for a nonexistent self entry in the leader's peer replication map. Existing ABD is not a reason to add/promote D again.
- Publish routing to ABD only after durable final uniform ABD membership is proven. The metadata publication compares the expected job/revision, so an old controller cannot overwrite a newer phase or unrelated directory update. Crash after membership and before metadata publication resumes by observing ABD, then publishes; it must not restore ABC.
- The existing gateway must refresh the revisioned directory and use D without restart. Its present startup-only directory is insufficient. Refresh and leader hints must never replay a handed uncertain mutation. Temporary unavailable results during the membership-before-map gap are honest; stale GET values and invented successful writes are not.
- Removed C may retain its bytes. Stop routing the moved data group to C and require fresh requests on C for that group to fail authority; physical deletion is unnecessary for the first move. C's process, catalog endpoint, metadata-group membership and sibling data groups remain in service. An overlapping read with a valid earlier barrier may still complete. Keep group-zero membership ABC unless a distinct metadata-group move is explicitly designed.

## Focused acceptance schedules

1. Bootstrap race: pause an old initializer before its proposal, complete normal bootstrap and a revised directory through the supported conditional path, then release the old initialization proposal. It cannot overwrite the new directory. Do not construct an impossible schedule where a later log entry applies before an earlier committed entry in the same group. Two competing transitions in the same apply iterable admit only the expected revision chain; conflict responses remain bounded. The final brief selects separate metadata chunks, so later metadata entries see the prior durable chunk instead of sharing one native batch.
2. First-job durability: accept J1, lose its reply, retry J1; reject conflicting target and new J2 even if its target equals J1. Restart controller and nodes, then repeat those checks. Delayed jobs cannot reset persisted progress or endpoint identity.
3. Learner proof: stall D replication and show no promotion; lose the leader while blocking add-learner waits and show a returned old success does not promote D. Reconcile on the new leader with fresh matched/barrier evidence. Old ABC requires an old quorum throughout; learner D never substitutes for C.
4. Controller delay: pause one executor before add-D and another before change-to-ABD; complete J1 elsewhere, restart the controller, then release both. Final voters remain uniform ABD, routing never regresses, and no RPC can add C back. Record actual full membership LogIds, not only job labels.
5. Publication crash cuts: lose membership response; restart before and after final uniform commit; crash before/after directory CAS. Publication never precedes final durable membership, repeats are idempotent, and membership success followed by metadata delay is recoverable.
6. Removed C and live routing: after confirming final membership and relevant partition, invoke fresh moved-group requests on C and require authority failure. Make D leader and verify the already running gateway refreshes placement and serves successful GET/PUT/DELETE. Rejoin stale C and verify it cannot form an independent authority for that group. Preserve committed values and deletes; unchanged sibling groups and metadata remain usable, including through C where it still participates.
7. Force D to catch up through a real snapshot plus tail, not only a short log. Run traffic during the move and check history with Unknown operations treated as incomplete, potentially committed writes. Process-crash evidence does not imply physical power-loss qualification.
